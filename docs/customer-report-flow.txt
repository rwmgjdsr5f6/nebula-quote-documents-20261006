================================================================

本说明只讲 report 这一个公开子命令：它怎样只读 SQLite、怎样做逐字符精确
筛选、怎样按客户分组累计、怎样排序，以及 JSON 与 HTML 两种输出各自的
确定结果。所有说明沿 README“按客户汇总报表”一节的公开入口展开，不新增、
不改写任何命令、参数或数据格式。

本次交付仅为这份文档：quote.py、README.md 及 save/preview/list/export/
report 的既有行为均未改动，产品代码无任何修改。

一、公开入口与“读库 → 筛选 → 分组 → 排序 → 输出”的关系
--------------------------------------------------------
公开命令（README.md:107-110；argparse 定义 build_parser，quote.py:736-750；
分发 main，quote.py:755-758）：

  python3 quote.py report --db <数据库> [--customer <客户原文>] [--output <HTML>]

处理函数为 cmd_report()（quote.py:619-697），HTML 由
render_report_html()（quote.py:554-616）渲染。五个阶段的顺序与位置：

  1. 前置校验：空白 --customer 拒绝（quote.py:622-624）；
     --output 已存在拒绝（quote.py:627-629）。两者都先于数据库访问。
  2. 读库：以只读 URI 打开（open_readonly_database，quote.py:212-217；
     调用点 quote.py:633），核对 quotes 表具备 number、customer、total
     三列（quote.py:638-646），然后无 WHERE、无 ORDER BY 地取出每张报价
     的客户与已存合计：SELECT customer, total FROM quotes
     （quote.py:649）。
  3. 精确筛选 + 分组：在 Python 中逐行进行——先按客户原文逐字符筛选
     （quote.py:663-664），再以客户原文为字典键累加“张数 +1、累计加
     total”（quote.py:659-666）。
  4. 排序：分组结果按客户原文的 UTF-8 字节序排列，等价于 SQLite BINARY
     排序（quote.py:670-675，排序键 encode("utf-8") 在 quote.py:673）。
  5. 输出：省略 --output 时写一行 JSON 数组到标准输出（quote.py:677-686）；
     指定 --output 时渲染 HTML 并以 O_EXCL 独占新建文件
     （render_report_html 调用在 quote.py:688；write_new_file 调用在
     quote.py:692）。

两个必须先记住的总体事实【源码】：
- 筛选、分组、排序全部发生在把 quotes 行取回 Python 之后；SQL 语句本身
  没有 WHERE 也没有 ORDER BY（quote.py:649）。这与 list 在 SQL 中筛选、
  排序的做法不同，但精确匹配的可观察结果一致。
- report 全程只读：open_readonly_database 使用 file:<绝对路径>?mode=ro
  （quote.py:214-215），代码路径中没有任何写库语句；items 表完全不参与，
  note 列也不读取。

  "customer": "演示<甲>&乙",

  "customer": "演示<甲>&乙",
  "items": [

q-r3.json：

{
  "number": "Q-R3",
  "customer": "合计",
  "items": [

保存命令（成功后标准输出逐行回显编号，退出码 0；README.md:9-11、33）：

  python3 quote.py save --db demo.sqlite --input q-r1.json

【实测】三条 save 的标准输出依次为 Q-R1、Q-R2、Q-R3（各占一行），

【测试】tests/test_report_total_flow.py:40-59 的 TOTAL_SAMPLES

三、无筛选 JSON：命令与确定结果
-------------------------------
命令（README.md:108；对应 quote.py:677-686 的输出分支）：

  python3 quote.py report --db demo.sqlite

确定输出（一行完整 JSON 数组，末尾恰好一个换行，无 HTML 文件产生）：

[{"customer": "合计", "quote_count": 1, "total": 700}, {"customer": "演示<甲>&乙", "quote_count": 2, "total": 2800}]

【实测】本次运行标准输出与上面逐字符一致（含 json.dumps 默认的

【源码】
- 每个客户一个对象，仅 customer、quote_count、total 三个键
  （quote.py:681-684）；客户原文 ensure_ascii=False 保留，只做 JSON
  所需转义，不做 HTML 转义，故“演示<甲>&乙”在 JSON 中裸出现
  （quote.py:685）。
- 张数与累计均为 JSON 整数、以分为单位，不换算为元、不是浮点或字符串
  （quote.py:665-666 用 Python int 累加，quote.py:685 直接序列化）。
- 顺序为“合计”在前、“演示<甲>&乙”在后：按客户原文 UTF-8 字节升序，
  “合”首字节 E5 小于“演”首字节 E6（quote.py:670-675）。
- 数组只有两个客户对象，没有第三个“全局合计”对象（见第六节之四）。
【测试】tests/test_report_total_flow.py:420-447 断言同一数据下 JSON
恰为两个对象（700 与 2800）、键集合固定、total 为 int、原文含
“演示<甲>&乙”且不生成 HTML；tests/test_report_flow.py:210-220
断言三字段白名单与整数类型。


四、无筛选 HTML：客户行与最后的合计行
-------------------------------------

  python3 quote.py report --db demo.sqlite --output report-all.html

成功后标准输出仅为 report-all.html 加一个换行，退出码 0，标准错误为空
【源码：print(output)，quote.py:696】。表格三列为客户、报价张数、

（quote.py:596、608）。确定的表格内容（tbody 两个客户行，tfoot 一个
合计行）：

  <tbody>
        <tr><td>合计</td><td class="num">1</td><td class="num">7.00</td></tr>
        <tr><td>演示&lt;甲&gt;&amp;乙</td><td class="num">2</td><td class="num">28.00</td></tr>
  </tbody>
  <tfoot>
      <tr><td>合计</td><td class="num">3</td><td class="num">35.00</td></tr>
  </tfoot>

【实测】本次生成的 report-all.html 中 <table>…</table> 片段与上面
逐字符一致（缩进亦同）。
要点（全部【源码】，render_report_html，quote.py:554-616）：
- 客户行由分组结果 records 生成（quote.py:566-575）；合计行在所有客户
  行之后单独放入 <tfoot>（quote.py:585-591），全页唯一（结构上 tbody 与
  tfoot 分离，quote.py:613）。
- 合计行三格为字面量“合计”、本次结果总张数、总金额（元）：
  total_count 与 total_amount 直接对 records 求和（quote.py:583-584），
  即 1+2=3 张、(700+2800)=3500 分 → format_yuan 显示 35.00
  （quote.py:589 调用 format_yuan，函数见 quote.py:251-253）。
- 客户原文“合计”是 tbody 中一个普通客户行（1 张、7.00 元），不被合计
  行替换或合并：它来自 records，与 tfoot 的固定标签“合计”只是同字
  （quote.py:567-574 对比 quote.py:587）。
- “演示<甲>&乙”经 html.escape 转义为“演示&lt;甲&gt;&amp;乙”
  （e = html.escape，quote.py:565；作用于客户单元格，quote.py:569）；
  单元格使用 white-space: pre-wrap 样式（quote.py:602），浏览器中显示
  原文且不产生任何标签或脚本。
【测试】tests/test_report_total_flow.py:63-67 以手写常量固定了同样的
两行客户格与 [合计, 3, 35.00] 合计格；同文件 :208-276 断言 tbody/
tfoot 位置、“合计”客户行恰出现一次、tfoot 全页唯一、转义片段出现而
裸“演示<甲>&乙”不出现，并核对合计恒等于各客户行之和。
另：tests/test_report_html_flow.py:186-202 把库内 total 篡改为 9999
后生成 HTML，页面显示 99.99，证明 HTML 金额取自已存 total 而非重算。

六、三个关键结论的源码依据（张数、累计金额、合计行）
----------------------------------------------------
1. 多条明细不增加张数。
   读库查询只 SELECT quotes 表的 customer、total，一张报价恰好贡献一行
   结果（quote.py:649）；分组循环对每个取回行只做一次 count + 1
   （quote.py:660、665-666），items 表在整个 cmd_report 中从不被查询。
   Q-R1 虽有两条明细，在“演示<甲>&乙”组内只计一张。
   【测试】tests/test_report_flow.py:175-183 先在库中自检 Q-B 有两条
   明细（前置条件）；同文件 :222-225 再断言 Demo 组 quote_count 为 2
   （两张报价、而非四条明细）；
   tests/test_report_html_flow.py:204-212 同样断言双明细报价张数为 1。

2. 零金额报价仍计入张数。
   分组对张数的累加是无条件的 +1，累计才加 total（quote.py:665-666），
   total 为 0 不影响计数。故 Q-R2（total=0）使演示客户组成为 2 张，
   累计仍是 2800 + 0 = 2800 分。
   【测试】tests/test_report_flow.py:64-70 的固定期望中 Demo 组含一张
   0 分报价、张数仍为 2（断言见 :222-225）；零金额元显示 0.00 的
   例子见 tests/test_report_html_flow.py:167-171。

3. 累计金额读取已存 total，不重新计算明细。
   累计值唯一来源是 quotes.total（quote.py:649 读出，quote.py:666
   累加）；report 不读 quantity、unit_price、line_amount，items 表无需
   存在。quotes.total 是 save 时 validate_quote() 的整数计算结果
   （行金额 quote.py:129，合计 quote.py:135；落库 quote.py:187-190）。
   【测试】tests/test_report_html_flow.py:186-202 篡改 total 为 9999
   后页面显示 99.99，直接锁定“读已存值”这一行为。

4. JSON 输出不增加全局合计对象。
   JSON 负载由 records 一对一映射而成（quote.py:681-684），records 是
   每个客户一个三元组（quote.py:670-675）；代码中不存在向列表追加
   “总计/合计”对象的语句，全局 3 张、3500 分只出现在 HTML 的 tfoot。
   【测试】tests/test_report_total_flow.py:428-440 断言 JSON 恰有两个
   客户对象、金额为 700 与 2800、无第三个汇总对象；
   tests/test_report_html_flow.py:494-512 断言省略 --output 不生成 HTML。

5. “合计”客户仍是独立客户行；尖括号与与号转义后显示原文。
   客户行与合计行分属 tbody/tfoot 两条渲染路径（quote.py:566-591），
   分组键对客户原文不做任何保留字处理，名为“合计”的客户照常成组
   （dict 键精确相等，quote.py:665）。客户文本统一经 html.escape
   （quote.py:565、569），<、> 变为 &lt;、&gt;，& 变为 &amp;，页面
   显示原文；pre-wrap 保留首尾/连续空白与换行（quote.py:602）。
   【测试】tests/test_report_total_flow.py:239-256；脚本注入样例
   tests/test_report_html_flow.py:469-488 断言客户中的标签只被转义、
   tbody 内除 tr/td 外无额外标签。


七、排序：客户原文 BINARY 升序，与保存顺序无关
----------------------------------------------
排序在 Python 中完成，键为客户原文的 UTF-8 字节串：
sorted(groups.items(), key=lambda item: item[0].encode("utf-8"))
（quote.py:670-675），源码注释明确说明其等价于 SQLite BINARY 排序
（quote.py:668-669）。本文样例保存顺序为 R1、R2、R3，输出顺序却为
“合计”客户在前（“合”E5 90 88）、“演示<甲>&乙”在后（“演”E6 BC 94），
与保存先后无关。JSON 数组顺序（第三节）与 HTML 客户行顺序（第四节）
都由这同一排序决定。
【测试】tests/test_report_flow.py:64-70、204-208 以“空格 < 大写 <
小写”的固定客户集断言 BINARY 顺序且与保存顺序无关。


八、空库与无匹配
----------------
JSON 形式（省略 --output）：records 为空时负载为空列表，标准输出为
[] 加恰好一个换行，退出码 0（quote.py:677-686；空 records 由
quote.py:659-675 的空分组自然产生）。
HTML 形式（--output）：保留 thead 表头三列（quote.py:611），tbody 为空
（quote.py:577-579 的 else 分支），表格后显示“没有匹配的报价”
（quote.py:579）；合计行照常输出，求和对空列表得到 0 张、
format_yuan(0) = 0.00 元（quote.py:583-589、251-253）。
【实测】本次对“只建表、无报价”的空库分别执行：
  python3 quote.py report --db empty.sqlite
    → 标准输出 [] 加换行，退出码 0；
  python3 quote.py report --db empty.sqlite --output empty.html
    → 退出码 0，页面含一次“没有匹配的报价”，tfoot 为
      <tr><td>合计</td><td class="num">0</td><td class="num">0.00</td></tr>；
  对三张报价库执行 report --customer 不存在（JSON 与 HTML 各一次）：
  JSON 为 [] 加换行；HTML 无客户行、有提示、合计行同为 0 张 0.00 元。
【测试】JSON 空库 tests/test_report_flow.py:245-261 与
tests/test_report_html_flow.py:514-524；HTML 空库/无匹配
tests/test_report_html_flow.py:218-245；空态合计行
tests/test_report_total_flow.py:317-358。


九、精确筛选的逐字符语义
------------------------
report 的筛选不是 SQL LIKE，而是取回全部行后在 Python 中做字符串精确
相等比较（quote.py:649 取全量；quote.py:663-664 的 != 判定）。由此
确定【源码】：
- 大小写敏感：Demo、demo、DEMO 是不同客户；
- 首尾空格、连续空格、换行逐字符参与比较，不做 strip 或归一化；
- % 与 _ 是普通字符，没有通配含义；筛选值原样比较，不存在子串匹配。
- 合法但无任何匹配的筛选值属于成功查询：输出空结果（见第八节），不是
  错误。
- 空白筛选（空字符串或纯空白）则在校验阶段拒绝：
  if customer_filter is not None and not customer_filter.strip():
      return fail("客户筛选值不能为空白")
  （quote.py:622-624）。该检查在读库之前；实际前置顺序为：空白校验
  （quote.py:622-624）→ 输出已存在校验（quote.py:627-629）→
  打开数据库（quote.py:633），因此空白拒绝时既不触碰数据库，也不可能
  创建 HTML。
【测试】筛选矩阵（HTML 侧）：tests/test_report_html_flow.py:251-259
（精确命中）、:261-288（含首尾空格与换行的客户原样可见）、
:290-312（% 与 _ 按普通字符，LIKE 风格串筛选落空）；空白拒绝且不碰
数据库/不建 HTML：:407-424（覆盖 ""、" "、"\t"、" \n\t "）。
【实测】--customer '   '（三个空格）时退出码 1、标准输出为空、

十、旧库兼容与超过 64 位的累计
------------------------------
旧库（缺 note 列或缺 items 表）：
- 结构检查只要求 quotes 表存在且含 number、customer、total 三列
  （quote.py:638-646）；查询只取 customer、total（quote.py:649），
  既不读 note 也不读 items，因此旧库缺 note 列、甚至没有 items 表都可
  直接汇总。
- 只读 URI（quote.py:212-217）决定了 report 不可能补列或建表：不补
  结构、不改任何记录。
【实测】手工建立只有 number/customer/total 三列、无 items 表的旧库并
插入一条（'Q-L'，'旧库%_客户 <x>&y'，1234）：report JSON 正常输出
该客户 1 张 1234 分；执行后 PRAGMA 仍只有三列、sqlite_master 中只有
quotes 表。
【测试】tests/test_report_flow.py:284-335（JSON：缺 note 列、无 items
表，汇总正确且结构/记录前后一致）、tests/test_report_html_flow.py:
349-384（HTML：转义与 12.34 元显示，确认不补 note、不建 items）。

累计超出有符号 64 位上限：
- 单张报价的 total 在 save 阶段不得超过 INT64_MAX = 2^63-1
  （quote.py:22、135-137）；但多张合法报价的分组累计在 Python 中用
  任意精度整数完成（quote.py:655-658 的注释说明了刻意不用 SQLite SUM
  的原因，累加在 quote.py:666），超界不溢出。
- JSON 直接写出完整十进制整数（quote.py:685）；HTML 经 format_yuan
  纯整数 //100 与 %100 换算（quote.py:251-253、571、589），不用浮点、
  不四舍五入。
【实测】为同一客户“大额”保存两张单价均为 9223372036854775807 分的
报价：JSON 输出 {"customer": "大额", "quote_count": 2,
"total": 18446744073709551614}；HTML 中唯一客户行为“大额 2 张
184467440737095516.14 元”，tfoot 合计行同为 2 张、
184467440737095516.14 元（客户行与合计行数值一致，因为只有一个客户）。
单张 INT64_MAX 分 = 92233720368547758.07 元的逐行显示由下述测试中
“两个不同客户各一张”的样例覆盖，本次未单独执行该形态。
【测试】tests/test_report_flow.py:341-371（JSON 精确输出
18446744073709551614，原文含完整数字）、tests/test_report_html_flow.py:
318-343（HTML 两位小数精确）、tests/test_report_total_flow.py:364-414
（两个不同客户时合计行精确为 2 张、184467440737095516.14 元，且不
出现科学计数法）。
