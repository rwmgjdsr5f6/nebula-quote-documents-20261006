一、链路完整性结论
------------------
“输入明细 JSON -> 保存到 SQLite -> 按编号取得 HTML 预览”这条链路在当前源码中
完整存在，由 quote.py 的子命令 save 与 preview 构成，二者可在不同进程中运行：

  保存：python3 quote.py save    --db <数据库路径> --input <JSON 路径>
  预览：python3 quote.py preview --db <数据库路径> --number <编号> --output <HTML 路径>

二、输入格式（save）
--------------------
输入为 UTF-8 编码的 JSON 文件，根元素必须是对象【源码：quote.py:76-77】，
必填字段【源码：quote.py:79-81】：

  number   字符串，去除首尾空白后非空（require_nonblank_str，quote.py:61-66）
  customer 字符串，同上
  items    数组，且至少 1 条（quote.py:96-100）

每个数组元素必须是对象（quote.py:105-106），必填字段（quote.py:107-109）：

  description 字符串，去除首尾空白后非空（quote.py:111）
  quantity    整数且不能是布尔值，必须 > 0（quote.py:113-117；is_plain_int 见 quote.py:56-58）
  unit_price  整数且不能是布尔值，必须 >= 0（允许 0）（quote.py:119-123）

可选字段 note（客户说明）【源码：quote.py:86-94】：
  - 省略 note 字段，或 note 为空字符串 ""：表示无说明，库中存 NULL
    （quote.py:88、93-94；写入时 note=None 直传，quote.py:186-189）。
  - note 为非空字符串（包括纯空白字符串）：原样保存，不做任何去除空白处理；
    预览中转义后显示（见第五节）。纯空白字符串不是空字符串，不在归并之列。
  - note 为 null 或任何其他非字符串值（数值、数组、对象、布尔等）：拒绝，
    走 fail()，标准输出为空，标准错误为“错误: note 必须是字符串”，退出码 1
    （quote.py:91-92、50-53）。此拒绝发生在打开数据库之前（校验在
    quote.py:170-173，打开数据库在 quote.py:176-179），不创建数据库文件。
    【实测】note 分别为 null 与数值 5 时，退出码均为 1，标准输出为空，
    标准错误均为“错误: note 必须是字符串”，目标数据库文件未生成。
    【测试】tests/test_note_flow.py:350（非法 note 类型拒绝且不建库）、
    tests/test_note_flow.py:365（非法 note 不改动已有数据库）。

其他源码可证的输入行为【源码】：
- “非空白”只用于判定合法性；合法文本原样保存，不做 trim（quote.py:61-66
  只返回原值，写入为参数直传，quote.py:186-199）。
- 金额单位为“分”的整数（模块文档字符串 quote.py:10；README.md:31）。
- 数量、单价的上界：quantity 或 unit_price 大于 INT64_MAX=(2**63-1) 即拒绝
  （quote.py:21、125-126）。乘积与合计另行检查（见下节）。
- JSON 中的 true/false 是布尔值，明确不算整数；1.5 这类浮点数也不算整数
  （quote.py:56-58、113-123）。
- 除 note 外的额外字段（如 total）不参与任何处理，直接忽略；合计永远由源码
  计算，不接受调用者提供（validate_quote 只读取上述已知字段，quote.py:69-138）。
- note 不参与金额计算：合计仅由明细行金额求和（quote.py:128-136），
  note 在校验返回值中单独传递（quote.py:138）。
- 对字符串长度、编号格式（无任何模式约束）、明细重复等均无检查（见第七节）。


三、整数金额计算与保存
----------------------
计算全部使用 Python 整数运算，不涉及浮点【源码：quote.py:128-136】：

  行合计 line_amount = quantity * unit_price           （quote.py:128）
  单据合计 total      = 所有行 line_amount 之和         （quote.py:134）

  - 行合计 > INT64_MAX：拒绝，“行金额超出有符号64位整数范围”（quote.py:129-130）
  - 合计   > INT64_MAX：拒绝，“合计金额超出有符号64位整数范围”（quote.py:135-136）
  数量、单价本身超界的检查在乘积之前（quote.py:125-126）。因 quantity>0、
  unit_price>=0，不存在负金额，故源码没有也不需要负数下界检查。

数据库结构（SCHEMA，quote.py:23-39；保存时由 ensure_schema 建表，quote.py:147-148）：

  quotes(number TEXT PRIMARY KEY, customer TEXT NOT NULL,
         total INTEGER NOT NULL, note TEXT)
  items(id INTEGER PRIMARY KEY AUTOINCREMENT,
        quote_number TEXT NOT NULL REFERENCES quotes(number),
        position INTEGER NOT NULL, description TEXT NOT NULL,
        quantity INTEGER NOT NULL, unit_price INTEGER NOT NULL,
        line_amount INTEGER NOT NULL)

  - 主表写入 number、customer、total、note（quote.py:186-189）。
  - 明细写入 position（enumerate 从 0 开始，quote.py:192-199）、说明、数量、
    单价、行合计。
  - 打开连接时执行 PRAGMA foreign_keys = ON（quote.py:143）。明细在同一事务内、
    主行插入成功之后才插入（quote.py:184-199）。

旧库兼容（保存侧）【源码：quote.py:147-152】：
  ensure_schema 在建表后检查 quotes 的列；旧库缺少 note 列时执行
  ALTER TABLE quotes ADD COLUMN note TEXT 就地补列，已有报价的 note 为 NULL
  （无说明），无需重建。补列与建表在独立事务中提交（quote.py:182-183），
  先于主表/明细写入事务（quote.py:184-199）。

成功时的公开结果：标准输出打印编号（print(number)，quote.py:207），退出码 0。
【测试】tests/test_amount_flow.py:115（正常流程保存后预览，含金额断言）。

编号如何确定【源码】：
  编号完全由输入 JSON 的 number 字段提供，原样作为主键，源码中不存在任何
  自动生成、自增、补零或查重后改名的逻辑（全文件仅 quote.py:207 一处
  print(number) 输出它，写入为直传；items.id 的 AUTOINCREMENT 是内部列，
  从不对外显示）。因此保存后“可观察到的编号”就是输入里的编号字符串。


四、同一编号再次保存的结果
--------------------------
quotes.number 是 PRIMARY KEY。重复保存同一编号时，主表 INSERT 触发
sqlite3.IntegrityError，被转换为 DuplicateNumber（quote.py:190-191），
最终走 fail()：标准错误输出“错误: 报价编号已存在: <编号>”，退出码 1，
标准输出为空（quote.py:200-201、50-53）。

该 INSERT 位于 with conn 事务中（quote.py:184），失败即回滚，明细的
executemany 不会执行，本次报价主行与明细均不写入，已有数据不变。
【测试】tests/test_duplicate_flow.py:244（重复提交被拒、原报价保持完整）、
tests/test_amount_flow.py:330（被拒的保存不改动已有数据库）。
当前源码没有更新/覆盖已存报价单的入口。

旧库上的重复保存（边界细节）【源码 + 实测】：
  对缺少 note 列的旧库执行 save 时，补列事务（quote.py:182-183）先于写入
  事务提交。若随后主表 INSERT 因编号重复失败，回滚的只是写入事务；
  已经提交的补列不会撤销——库中此后带有 note 列，但本次报价与明细均未写入。
  【实测】在只有 number/customer/total 三列、含一条旧报价的旧库上：第一次
  save 新编号成功后 quotes 出现 note 列；再用同一编号 save，退出码 1，
  标准错误“错误: 报价编号已存在: <编号>”，库中报价行数与明细行数不变，
  note 列保留。


五、预览流程（preview）与数据来源
---------------------------------
处理顺序【源码：quote.py:275-343】：

1. 输出目标已存在 -> 立即拒绝（quote.py:276-278）。此检查在打开数据库之前，
   故“输出已存在”优先于“编号不存在”。
2. 以只读 URI 打开数据库：file:<绝对路径>?mode=ro（quote.py:280-284）。
   数据库文件不存在或不可访问时抛 sqlite3.Error，报“无法读取数据库 ...”，
   退出码 1，且不创建数据库文件、不创建输出文件。
3. 按编号原文精确匹配取主行（quote.py:285-301）。旧库兼容：先查
   PRAGMA table_info(quotes)，有 note 列则 SELECT customer, total, note，
   否则 SELECT customer, total, NULL（quote.py:285-296）——旧库缺少 note 列
   时可直接预览，一律按无说明处理，只读打开不补列、不改动库结构。
   【实测】对无 note 列的旧库直接 preview 成功（退出码 0），生成页面无
   “客户说明”区域，预览后库结构仍只有 number/customer/total 三列。
   【测试】tests/test_note_flow.py:487（旧库先预览再带说明保存）。
   查不到编号 -> “错误: 报价编号不存在: <编号>”，退出码 1，
   不产生输出文件（quote.py:297-300）。
4. 取明细：SELECT description, quantity, unit_price, line_amount FROM items
   WHERE quote_number=? ORDER BY position（quote.py:302-306），即严格按保存时的
   输入顺序（position 升序）。
5. render_html() 渲染（quote.py:216-272），再以 os.open(..., O_WRONLY|O_CREAT|
   O_EXCL) 独占新建输出文件（quote.py:313-317）。O_EXCL 是并发兜底：目标存在
   绝不覆盖。写循环处理部分写入（quote.py:319-340）。成功后标准输出输出路径，
   退出码 0（quote.py:342）。

预览内容取自哪份数据【源码】：
  客户、合计、说明取自 quotes 行；说明、数量、单价、行合计全部取自 items 行
  （quote.py:288-306、311）。也就是说预览只反映此前已保存的数据，
  保存与预览之间没有任何内存态共享。唯一例外是页面中的“编号”：渲染用的是
  命令行传入的 args.number（quote.py:311），不是库内回读值；由于查询本身按该
  值精确匹配，正常情况下二者必然相同。

说明（note）在页面中的位置与形态【源码：quote.py:228-239】：
  说明非空时，在客户信息（<dl>）之后、明细表格（<table>）之前出现
  “客户说明”区域（quote.py:259 的 {note_section} 位置），正文放在
  <p class="note-text"> 内，样式 white-space: pre-wrap（quote.py:233）
  保留空格与换行；说明文本经 html.escape 转义（quote.py:237）。
  说明为 NULL（省略或空字符串保存的）时不出现该区域，页面其余内容与样式
  与无说明情形一致（quote.py:230-232）。
  【测试】tests/test_note_flow.py:221（保存后预览的说明往返）、
  tests/test_note_flow.py:263（省略/空说明不出现该区域）、
  tests/test_note_flow.py:290（纯空白说明照样保存并显示）。

HTML 文本转义发生的位置【源码】：
  render_html 内把 html.escape 别名为 e（quote.py:217），作用于全部用户文本：
  - <title> 中的编号（quote.py:244）
  - 正文中的编号（quote.py:256）
  - 客户（quote.py:257）
  - 说明 note（quote.py:237）
  - 每条明细的说明（quote.py:221）
  数量与金额是整数经格式函数生成，不经转义。Python 标准库 html.escape 默认
  quote=True：转义 & < >，并把 " 转成 &quot;、' 转成 &#x27;。
  【测试】tests/test_preview_flow.py:128（用户文本转义）。

金额换算（分 -> 元）【源码】：
  format_yuan(cents) = f"{cents // 100}.{cents % 100:02d}"（quote.py:211-213），
  纯整数除法与取模，保留两位小数，无浮点。单价、行合计、总计三处都经此函数
  （quote.py:223-224、267）。
  【测试】tests/test_amount_flow.py:165（INT64_MAX 边界换算往返）。
  表格行号为 position+1（首行显示 1，quote.py:220）。


六、同一编号再次生成预览的结果
------------------------------
- 输出到同一路径：因目标已存在，在查库之前即被拒绝，“错误: 输出文件已存在:
  <路径>”，退出码 1，原文件保持不变（quote.py:276-278）。
- 输出到新的路径：成功，退出码 0。内容完全由库内已保存数据重新渲染。
  预览本身不写数据库，重复预览不会改变任何数据（只读打开，quote.py:280-284）。
  【测试】tests/test_preview_flow.py:226（新路径内容一致、已存在或未知编号被拒）。
- 不存在“重新计算”：预览显示的行合计/合计是保存时落库的整数值，不是预览时
  重新相乘得到（SQL 直接读 line_amount、total，quote.py:288-306）。

九、合成样例（端到端核对，本次实际执行）
----------------------------------------
下列输入当前实现完全支持。客户文本含 <甲>&乙，note 含首尾空格与换行，
两条明细分别为数量 2、单价 1250 分与数量 1、单价 300 分。

输入文件 quote.json（UTF-8）：

{
  "number": "Q-DOC-001",
  "customer": "<甲>&乙",
  "note": "  含税价\n含运费  ",
  "items": [
    {"description": "零件A", "quantity": 2, "unit_price": 1250},
    {"description": "零件B", "quantity": 1, "unit_price": 300}
  ]
}

调用方式（在仓库根目录；数据库与输出路径可任指空目录）：

  python3 quote.py save    --db demo.sqlite --input quote.json
  python3 quote.py preview --db demo.sqlite --number Q-DOC-001 --output preview.html

【实测】可观察结果（本次在 /tmp 临时目录运行）：
  save    退出码 0，stdout 仅一行：Q-DOC-001，stderr 为空
  preview 退出码 0，stdout 仅一行：preview.html，stderr 为空；生成 UTF-8 HTML

编号：Q-DOC-001 就是输入 number 的原文，不是动态生成【源码：quote.py:83、
186-189、207——无任何编号生成代码】。

金额（规则与结果）：
  行合计 = 2 × 1250 = 2500；1 × 300 = 300（分）   依据 quote.py:128
  合计   = 2500 + 300 = 2800（分）                 依据 quote.py:134
  【实测】库内 quotes.total = 2800（整数分）；items 两行为
  (position 0, 零件A, 2, 1250, 2500)、(position 1, 零件B, 1, 300, 300)，
  note 列为原文 "  含税价\n含运费  "（首尾空格与换行逐字符保留）。
  HTML 显示：单价 12.50、3.00 元；行金额 25.00、3.00 元；总计 28.00 元
            依据 quote.py:211-213（//100 与 %100 两位补零）、223-224、267
  数量列显示整数 2、1；行号列显示 1、2（position 0/1 + 1） 依据 quote.py:220-222

文本转义（【实测】生成 HTML 源文中的关键片段）：
