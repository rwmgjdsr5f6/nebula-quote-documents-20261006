报价单保存与 HTML 预览流程说明（与冻结源码逐项核对）
======================================================

核对基准
--------
- 产品源码：quote.py（本仓库根目录，唯一可执行源码，全文 312 行）
- 公开文档：README.md
- 回归测试：tests/test_amount_flow.py（python3 -m unittest discover -s tests，4 个用例，核对时全部通过）
- 存储：本地 SQLite 文件，由命令行 --db 指定路径；仓库内不附带任何数据库或业务数据
- 本说明中的行号均以当前冻结版本 quote.py 为准；所有“实测”结果均为在仓库外临时目录用公开命令运行所得，产品源码、文档、数据库结构与数据未被修改。


一、链路完整性结论
------------------
“输入明细 JSON -> 保存到 SQLite -> 按编号取得 HTML 预览”这条链路在当前源码中**完整存在**，
由 quote.py 的两个子命令 save 与 preview 构成，二者可在不同进程中运行：

  保存：python3 quote.py save    --db <数据库路径> --input <JSON 路径>
  预览：python3 quote.py preview --db <数据库路径> --number <编号> --output <HTML 路径>

公开入口与实际处理位置的对应关系：

  命令行入口（argparse 定义）  build_parser()   quote.py:286-301
  分发                         main()           quote.py:304-307
  save 的处理函数             cmd_save()       quote.py:137-187
  preview 的处理函数          cmd_preview()    quote.py:242-283
  文档中的入口说明            README.md:9-11（save）、README.md:34-36（preview）

save 内部各环节位置：
  读取输入文件                cmd_save()            quote.py:139-142
  解析 JSON                  cmd_save()            quote.py:145-147
  输入校验与金额计算          validate_quote()      quote.py:66-124（调用点 quote.py:150）
  打开/建库                   open_database()、ensure_schema()  quote.py:127-134、161-162
  写入报价主表与明细          cmd_save()            quote.py:163-178

preview 内部各环节位置：
  输出目标占用检查            cmd_preview()         quote.py:244-245

二、输入格式（save）
--------------------
输入为 UTF-8 编码的 JSON 文件，根元素必须是对象（quote.py:72-73），必填字段
（quote.py:75-77）：

  number   字符串，去除首尾空白后非空（require_nonblank_str，quote.py:58-63）
  customer 字符串，同上
  items    数组，且至少 1 条（quote.py:83-86）

每个数组元素必须是对象（quote.py:91-92），必填字段（quote.py:93-95）：

  description 字符串，去除首尾空白后非空（quote.py:97）
  quantity    整数且不能是布尔值，必须 > 0（quote.py:99-103；is_plain_int 见 quote.py:53-55）
  unit_price  整数且不能是布尔值，必须 >= 0（允许 0）（quote.py:105-109）

其他源码可证的输入行为：
- “非空白”只用于判定合法性；合法文本原样保存，不做 trim。实测客户 "  张 三 " 与
  说明 " 服务 " 入库后逐字符保留（依据 quote.py:58-63 只返回原值，写入为参数直传）。
- 金额单位为“分”的整数（模块文档字符串 quote.py:8；README.md:28）。
- 数量、单价的上界：quantity 或 unit_price 大于 INT64_MAX=(2**63-1) 即拒绝
  （quote.py:19、111-112）。乘积与合计另行检查（见下节）。
- JSON 中的 true/false 是布尔值，明确不算整数；1.5 这类浮点数也不算整数
  （quote.py:53-55；tests/test_amount_flow.py:191-194）。
- 输入中的额外字段（如 total、note）不参与任何处理，直接忽略；合计永远由源码计算，
  不接受调用者提供（validate_quote 只读取上述已知字段，quote.py:66-124）。
- 对字符串长度、编号格式（无任何模式约束）、明细重复等均无检查（见第七节）。


三、整数金额计算与保存
----------------------
计算全部使用 Python 整数运算，不涉及浮点（quote.py:114-122）：

  行合计 line_amount = quantity * unit_price           （quote.py:114）
  单据合计 total      = 所有行 line_amount 之和         （quote.py:120）

  - 行合计 > INT64_MAX：拒绝，“行金额超出有符号64位整数范围”（quote.py:115-116）
  - 合计   > INT64_MAX：拒绝，“合计金额超出有符号64位整数范围”（quote.py:121-122）
  数量、单价本身超界的检查在乘积之前（quote.py:111-112）。因 quantity>0、
  unit_price>=0，不存在负金额，故源码没有也不需要负数下界检查。

数据库结构（SCHEMA，quote.py:21-36；保存时由 ensure_schema 建表，quote.py:133-134）：

  quotes(number TEXT PRIMARY KEY, customer TEXT NOT NULL, total INTEGER NOT NULL)
  items(id INTEGER PRIMARY KEY AUTOINCREMENT,
        quote_number TEXT NOT NULL REFERENCES quotes(number),
        position INTEGER NOT NULL, description TEXT NOT NULL,
        quantity INTEGER NOT NULL, unit_price INTEGER NOT NULL,
        line_amount INTEGER NOT NULL)

  - 主表写入 number、customer、total（quote.py:165-168）。
  - 明细写入 position（enumerate 从 0 开始，quote.py:171-178）、说明、数量、单价、行合计。
  - 打开连接时执行 PRAGMA foreign_keys = ON（quote.py:129）。明细在同一事务内、
    主行插入成功之后才插入（quote.py:163-178）。

成功时的公开结果：标准输出打印编号（print(number)，quote.py:186），退出码 0。
实测与 tests/test_amount_flow.py:122-138 一致：数量 2/1/4、单价 1250/300/0（分）
得到行合计 2500/300/0、合计 2800（分），库内均为整数。

编号如何确定：
  编号**完全由输入 JSON 的 number 字段提供**，原样作为主键，源码中不存在任何
  自动生成、自增、补零或查重后改名的逻辑（全文件仅一处 print(number) 输出它，
  写入为直传；items.id 的 AUTOINCREMENT 是内部列，从不对外显示）。因此保存后
  “可观察到的编号”就是输入里的编号字符串，没有动态编号规则可言。


四、同一编号再次保存的结果
--------------------------
quotes.number 是 PRIMARY KEY。重复保存同一编号时，主表 INSERT 触发
sqlite3.IntegrityError，被转换为 DuplicateNumber（quote.py:169-170），
最终走 fail()：标准错误输出“错误: 报价编号已存在: <编号>”，退出码 1，
标准输出为空（quote.py:179-180、47-50）。

该 INSERT 位于 with conn 事务中（quote.py:163），失败即回滚，明细的
executemany 不会执行。实测对同一编号第二次 save 后，库中 quotes 与 items
均仍只有原 1 行；回归测试 tests/test_amount_flow.py:211-257 也断言无效或重复
提交后已有数据库内容逐字节不变。当前源码**没有更新/覆盖已存报价单的入口**。


五、预览流程（preview）与数据来源
---------------------------------
处理顺序（quote.py:242-283）：

1. 输出目标已存在 -> 立即拒绝（quote.py:244-245）。此检查在打开数据库之前，
   故“输出已存在”优先于“编号不存在”。实测两者同时成立时报“输出文件已存在”。
2. 以只读 URI 打开数据库：file:<绝对路径>?mode=ro（quote.py:248-250）。
   数据库文件不存在或不可访问时抛 sqlite3.Error，报“无法读取数据库 ...”，
   退出码 1，且不创建数据库文件、不创建输出文件（实测）。
3. 按编号原文精确匹配取主行：SELECT customer, total FROM quotes WHERE number=?
   （quote.py:252-256）。查不到 -> “错误: 报价编号不存在: <编号>”，退出码 1，
   不产生输出文件（quote.py:257-259）。
4. 取明细：SELECT description, quantity, unit_price, line_amount FROM items
   WHERE quote_number=? ORDER BY position（quote.py:261-265），即严格按保存时的
   输入顺序（position 升序）。
5. render_html() 渲染（quote.py:195-239），再以 os.open(..., O_WRONLY|O_CREAT|
   O_EXCL) 独占新建输出文件（quote.py:273-278）。O_EXCL 是并发兜底：目标存在
   绝不覆盖。成功后标准输出输出路径，退出码 0（quote.py:282）。

预览内容取自哪份数据：
  客户、合计取自 quotes 行；说明、数量、单价、行合计全部取自 items 行
  （quote.py:253、261-265、270）。也就是说预览只反映**此前已保存**的数据，
  保存与预览之间没有任何内存态共享。唯一例外是页面中的“编号”：渲染用的是
  命令行传入的 args.number（quote.py:270），不是库内回读值；由于查询本身按该
  值精确匹配，正常情况下二者必然相同。

HTML 文本转义发生的位置：
  render_html 内把 html.escape 别名为 e（quote.py:196），作用于全部用户文本：
  - <title> 中的编号（quote.py:211）
  - 正文中的编号（quote.py:223）
  - 客户（quote.py:224）
  - 每条明细的说明（quote.py:201）
  数量与金额是整数经格式函数生成，不经转义。Python 标准库 html.escape 默认
  quote=True：转义 & < >，并把 " 转成 &quot;、' 转成 &#x27;。实测
  “<演示客户&Co>”显示源文为 &lt;演示客户&amp;Co&gt;，“<零件>”为
  &lt;零件&gt;，页面渲染时显示原文，不产生标签或脚本。

金额换算（分 -> 元）：
  format_yuan(cents) = f"{cents // 100}.{cents % 100:02d}"（quote.py:190-192），
  纯整数除法与取模，保留两位小数，无浮点。单价、行合计、总计三处都经此函数
  （quote.py:202-203、234）。实测 1250 分显示 12.50，2500 分显示 25.00；
  边界 INT64_MAX 分显示 92233720368547758.07（tests/test_amount_flow.py:165-183）。
  表格行号为 position+1（首行显示 1，quote.py:199）。


六、同一编号再次生成预览的结果
------------------------------
- 输出到**同一路径**：因目标已存在，在查库之前即被拒绝，“错误: 输出文件已存在:
  <路径>”，退出码 1，原文件保持不变（quote.py:244-245；实测一致）。
- 输出到**新的路径**：成功，退出码 0。内容完全由库内已保存数据重新渲染；实测
  两次生成的文件逐字节相同（diff 无差异）。预览本身不写数据库，重复预览不会
  改变任何数据（只读打开，quote.py:248-250）。
- 不存在“重新计算”：预览显示的行合计/合计是保存时落库的整数值，不是预览时
  重新相乘得到（SQL 直接读 line_amount、total，quote.py:253、262）。

源码**没有**专门处理、因此不享受“错误:”约定的情况（实测，明确列出，不虚构约定）：
- 输入文件不是合法 UTF-8：open(..., encoding="utf-8") 读取时抛 UnicodeDecodeError。
  它不属于被捕获的 json.JSONDecodeError 或 OSError，进程以**未捕获异常的
  traceback** 结束、退出码 1，stderr 没有“错误:”前缀；数据库尚未打开，不留库文件。
  这是输入侧唯一观察到的 traceback 出口（quote.py:139-147 的捕获范围决定）。
- 对编号/文本的长度与字符集、items 内重复明细、number 的格式模式，均无任何校验
  （validate_quote 中没有相应代码）。
- preview 的 --number 不做格式校验，直接原文精确匹配（quote.py:252-256、297）。
- --output 不校验扩展名或内容类型（quote.py:298 仅要求提供该参数）。

尚未实现的能力（在 quote.py 与 README.md 中均无对应代码或入口，不代为设计）：
- 报价单的修改、更新保存、删除；编号自动生成；报价单列表/查询全部报价；
  除“按编号取单个 HTML”之外的其他输出形式。save 仅支持 INSERT 新编号，
  preview 仅支持按主键读取并落一个新 HTML 文件。

九、合成样例（端到端核对）
--------------------------
下列输入当前实现完全支持。客户文本含 <演示客户&Co>，明细名称含 <零件>，
数量 2、单价 1250（分，即整数最小单位）。

输入文件 quote.json（UTF-8）：

{
  "number": "Q-SYNTH-001",
  "customer": "<演示客户&Co>",
  "items": [
    {"description": "<零件>", "quantity": 2, "unit_price": 1250}
  ]
}

调用方式（在仓库根目录；数据库与输出路径可任指空目录）：

  python3 quote.py save    --db demo.sqlite --input quote.json
  python3 quote.py preview --db demo.sqlite --number Q-SYNTH-001 --output preview.html

实测可观察结果：
  save    退出码 0，stdout 仅一行：Q-SYNTH-001
  preview 退出码 0，stdout 仅一行：preview.html；生成 UTF-8 HTML 文件

编号：Q-SYNTH-001 就是输入 number 的原文，不是动态生成（核对 quote.py:79、
166、186——无任何编号生成代码）。

金额（规则与结果）：
  行合计 = 2 × 1250 = 2500（分）   依据 quote.py:114
  合计   = 2500（分，仅一行）       依据 quote.py:120
  HTML 显示：单价 1250 -> 12.50 元；行合计 2500 -> 25.00 元；总计 25.00 元
            依据 quote.py:190-192（//100 与 %100 两位补零）、202-203、234
  数量列显示整数 2；行号列显示 1（position 0 + 1） 依据 quote.py:199、202

文本转义（实测 HTML 源文中的确定结果）：
  客户：&lt;演示客户&amp;Co&gt;   依据 quote.py:224 调用 html.escape
  说明：&lt;零件&gt;             依据 quote.py:201
  编号在 <title> 与正文各出现一次，原样 Q-SYNTH-001  依据 quote.py:211、223

如何顺着源码复核这一结果：
  校验/计算：validate_quote quote.py:66-124（重点 99-122）
  落库：quote.py:165-178；可用 sqlite3 直查 quotes.total=2500、
        items=(position0, "<零件>", 2, 1250, 2500)（tests:73-88 有同款查法）
  取数：quote.py:252-265
  渲染：render_html quote.py:195-239；转义别名 e 定义于 196 行
  也可直接运行 python3 -m unittest discover -s tests，其中
  test_normal_flow_save_then_preview（tests:115-163）覆盖 2×1250=2500、
  合计 2800 与 12.50/25.00/28.00 的显示断言。

再次操作的边界（同一样例）：
  - 用同一 JSON 再跑一次 save：拒绝，“错误: 报价编号已存在: Q-SYNTH-001”，
    退出码 1，库内仍只有 1 张报价、1 条明细（quote.py:169-180）。
  - 再跑 preview 指向同一 preview.html：拒绝，“错误: 输出文件已存在”，退出码 1
    （quote.py:244-245）；换一个新 --output 路径则成功，且内容与首份逐字节相同，
    因为内容只来自库内已保存行（quote.py:248-270）。
  - 把 --number 换成未保存过的值：拒绝，“错误: 报价编号不存在: ……”，退出码 1，
    不生成文件（quote.py:257-259）。
