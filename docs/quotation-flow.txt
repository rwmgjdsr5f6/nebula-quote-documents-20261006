======================================================

--------

一、链路完整性与公开入口
------------------------
“读取 JSON -> 校验明细与整数金额 -> 保存主表与明细 -> 按编号只读查询 ->
生成 HTML”这条链路在当前源码中完整存在，由 save 与 preview 两个子命令构成，
可在不同进程中运行，预览只依赖库内已保存的数据：

  保存：python3 quote.py save    --db <数据库路径> --input <JSON 路径>
  预览：python3 quote.py preview --db <数据库路径> --number <编号> --output <HTML 路径>

二、save（一）：读取与解码 JSON——含非法 UTF-8 边界
---------------------------------------------------
[源码] cmd_save 首先用 open(args.input, encoding="utf-8") 读取整份输入
（quote.py:156-158），随后才 json.loads（:165-166）、validate_quote
（:170-171），最后才 open_database（:177；:175 注释“校验全部通过后才触碰
数据库”）。以下三类失败都在打开数据库之前就结束进程：

- 文件不存在/不可读：捕获 OSError，stderr 输出
  “错误: 无法读取输入文件 <--input 原文>: <系统原因>”，退出码 1
  （quote.py:159-160，经 fail() :50-53）。
- 非法 UTF-8：严格 UTF-8 解码抛出 UnicodeDecodeError 即被捕获，stderr 输出
  “错误: 输入文件不是有效的 UTF-8: <--input 路径原文>”，退出码 1，标准输出
  为空，不忽略、不替换任何字节（quote.py:161-163）。由于此处在 open_database
  （:177）之前，即使 --db 指向不存在的目录，也不会创建数据库文件或其父目录。
  [测试] tests/test_amount_flow.py:282-300 精确断言退出码、空 stdout 与该行
  stderr（路径原样回显）；:302-317 覆盖文件开头、字符串中间的 0xFF 与末尾残缺
  序列三种非法位置；:324-328 证明编码错误先于数据库错误（--db 父目录不存在时
  仍只报编码错误）；:330-356 证明已有库不被改动。
  [本次] 以 0xFF 开头的输入实测一致：退出码 1、stdout 为空、stderr 恰为
  “错误: 输入文件不是有效的 UTF-8: /tmp/.../bad-utf8.json”加换行，无
  traceback，--db 所在的不存在父目录未被创建（附录 C）。
- JSON 语法错误：捕获 json.JSONDecodeError，stderr 输出“错误: JSON 解析失败:
  ……”，退出码 1，同样不触碰数据库（quote.py:165-168）。
  [测试] tests/test_amount_flow.py:385-397。


三、save（二）：校验输入——根对象、必填字段、note 规则、明细与整数金额
----------------------------------------------------------------------
[源码] 校验全部集中在 validate_quote()（quote.py:69-138），任一项不满足即抛
ValidationError，由 cmd_save 经 fail() 输出“错误: <原因>”并以退出码 1 返回
（quote.py:170-173）；校验阶段尚未打开数据库。

3.1 根对象与必填字段（quote.py:76-84）
- 根元素必须是 JSON 对象，否则“输入根元素必须是 JSON 对象”（:76-77）。
- number、customer、items 三个字段必须存在，否则“缺少必填字段: <字段名>”
  （:79-81）。
- number、customer 经 require_nonblank_str（:61-66）：必须是字符串
  （否则“<编号|客户>必须是字符串”），且 strip() 后非空（否则“不能只有空白”）。
  “非空白”只用于合法性判定；合法文本原样返回、原样入库，不做 trim（:61-66
  只返回原值）。

3.2 note 字段规则（quote.py:86-94）
- 省略 note 字段：合法，表示无说明，内部记为 None，入库为 SQL NULL（:88-89）。
- note 为空字符串 ""：合法，等价于无说明，归一化为 None 后入库 NULL（:93-94）。
- note 为非空字符串（包括纯空格、纯换行及其组合）：合法，原样保留，不做
  strip、不折叠空白（:90-92 只检查类型）。note 不参与任何金额计算，
  validate_quote 的行金额与合计只由 items 推导（:128-136）。
- note 为 null 或任何非字符串值（数字、布尔、数组、对象等）：拒绝，stderr
  恰为“错误: note 必须是字符串”，退出码 1，标准输出为空（:91-92）。
  [测试] tests/test_note_flow.py:221-261（非空说明含首尾空格、换行、尖括号的
  保存与预览）、:263-388（省略与空字符串：入库 NULL、预览无说明区域）、
  :290-305（纯空白说明 "  \n\n " 仍原样保存并显示）；非法类型见
  :330-363（null、42、true、数组、对象逐子例断言退出码 1、stdout 空、stderr
  恰为“错误: note 必须是字符串\n”，且不新建数据库文件）与 :365-406（对已有库
  反复拒绝后，已有报价与明细保持不变）。
  [本次] null 拒绝（附录 B）、空字符串/省略入库 NULL、纯空白 "  \n " 原样保存
  （附录 F）均与上述一致。

3.3 明细数组与每条明细（quote.py:96-132）
- items 必须是数组（:97-98）且至少 1 条，空数组报“明细不能为空”（:99-100）。
- 每个元素必须是对象（:105-106），且必须含 description、quantity、unit_price
  三个字段（:107-109）。
- description 经 require_nonblank_str：必须为字符串且 strip 后非空，合法值
  原样保留（:111）。
- quantity 必须是“纯整数”且 > 0（:113-117）；unit_price 必须是纯整数且
  >= 0（允许 0，:119-123）。is_plain_int（:56-58）要求 isinstance(int) 且不是
  bool：JSON 的 true/false、1.5 之类浮点数、字符串都不算整数。
- 64 位上界：quantity 或 unit_price 大于 INT64_MAX=(2**63-1)（quote.py:21）即
  拒绝（:125-126）。
  [测试] tests/test_amount_flow.py:187-257 汇总覆盖空白、布尔、浮点、越界等
  拒绝路径，并断言被拒后已有数据库内容不变；:165-185 覆盖 INT64_MAX 边界。

3.4 整数金额（quote.py:128-136）
  行金额 line_amount = quantity * unit_price          （:128，Python 整数运算）
  合计     total      = 各行 line_amount 之和          （:134）
- 行金额 > INT64_MAX：拒绝，“第 N 条明细的行金额超出有符号64位整数范围”
  （:129-130）。
- 合计 > INT64_MAX：拒绝，“合计金额超出有符号64位整数范围”（:135-136）。
- 因 quantity>0、unit_price>=0，不存在负金额，源码无负数下界检查。
- 合计永远由源码计算：输入 JSON 中即使带 total 等额外字段也不被读取
  （validate_quote 只取上述已知字段，:76-136）。注意 note 是当前唯一被读取的
  可选根字段；除此以外的额外字段一律不参与处理。


四、save（三）：建库、旧库补列、写入主表与明细、重复编号
--------------------------------------------------------
4.1 表结构（SCHEMA，quote.py:23-39；保存时由 ensure_schema 执行，:147-148）
  quotes(number TEXT PRIMARY KEY, customer TEXT NOT NULL,
         total INTEGER NOT NULL, note TEXT)
  items(id INTEGER PRIMARY KEY AUTOINCREMENT,
        quote_number TEXT NOT NULL REFERENCES quotes(number),
        position INTEGER NOT NULL, description TEXT NOT NULL,
        quantity INTEGER NOT NULL, unit_price INTEGER NOT NULL,
        line_amount INTEGER NOT NULL)
  打开连接即执行 PRAGMA foreign_keys = ON（open_database，quote.py:143）。

4.2 补列时机（quote.py:181-183）
  ensure_schema 先用 CREATE TABLE IF NOT EXISTS 建表（:148），再以
  PRAGMA table_info(quotes) 检查列集合：旧库缺少 note 列时执行
  ALTER TABLE quotes ADD COLUMN note TEXT（:150-152），已有报价的 note 即为
  NULL，不重建表、不迁移数据。补列只在 save 路径发生；preview 以只读方式打开，
  不补列（见第五节）。

4.3 两个独立事务（quote.py:182-199）——旧库重复编号边界的关键
  第一个 `with conn:` 只做 ensure_schema（:182-183），建表/补列在该事务结束时
  即已提交；第二个 `with conn:`（:184-199）才插入主行与明细：
  - INSERT quotes（:186-189）触发 sqlite3.IntegrityError 时转换为
    DuplicateNumber（:190-191），明细 executemany（:192-199）不会执行，整个
    第二事务回滚；最终 stderr 输出“错误: 报价编号已存在: <编号>”，退出码 1、
    stdout 为空（:200-201，fail :50-53）。
  - 当前结构的库上重复保存：本次报价的主行与明细均不写入，旧数据逐行不变；
    源码没有更新/覆盖已存报价的入口。
    [测试] tests/test_duplicate_flow.py:244-298（相同 JSON 与同编号变更内容
    两次提交都被拒，quotes/items 快照不变，拒绝后重新预览与基准逐字节一致）；
    事务边界另见 tests/test_save_failure_flow.py:215-445（第二条明细写失败时
    主行与全部明细整体回滚、自增序列不推进）。
    [本次] Q-DOC-001 第二次 save 实测退出码 1、stdout 空、stderr 为
    “错误: 报价编号已存在: Q-DOC-001”（附录 E）。
  - 旧库（无 note 列）上重复编号保存的组合行为：第一个事务的补列已经提交，
    第二个事务回滚不会撤销它。因此结果是——退出码 1、stderr“错误: 报价编号
    已存在: <编号>”，本次报价与明细不写入，但 quotes 表已新增 note 列，原有
    报价 note 为 NULL。该“补列保留”的组合没有现成测试用例直接断言：
    [测试] 分别覆盖了“重复回滚”（test_duplicate_flow）与“旧库补列成功”
    （test_note_flow.py:487-578），二者的交叉点为 [源码] 两个独立 with conn
    事务推导（quote.py:182-199）加 [本次] 实测确认（附录 D）。
  - 其他 sqlite3.Error：stderr“错误: 数据库写入失败: ……”，退出码 1
    （quote.py:202-203）；连接在 finally 中关闭（:204-205）。

4.4 成功输出
  print(number) 向标准输出打印输入编号原文加换行，退出码 0（quote.py:207）。
  编号完全由输入 JSON 的 number 提供并原样作为主键，源码中不存在自动生成、
  补零或改名逻辑（全文件仅 :207 一处输出编号；items.id 的 AUTOINCREMENT 是
  内部列，从不对外显示）。
  明细 position 为 enumerate(items) 从 0 开始的下标（:197），即严格保持输入
  顺序。


五、preview（一）：只读打开与按编号查询
---------------------------------------
[源码] cmd_preview（quote.py:275-343）处理顺序：

1. 输出目标已存在 -> 立即拒绝：os.path.exists 命中即 fail（quote.py:276-278），
   stderr“错误: 输出文件已存在: <路径>”，退出码 1。此检查在打开数据库之前，
   故“输出已存在”优先于“编号不存在”。
   [测试] tests/test_preview_flow.py:226-301、tests/test_write_flow.py:302-310。
   [本次] 对已存在的 preview.html 再生成，实测退出码 1、原文件不变（附录 E）。
2. 以只读 URI 打开数据库：file:<绝对路径>?mode=ro（quote.py:280-283）。数据库
   文件不存在或不可访问时不创建任何文件，统一报“错误: 无法读取数据库 ……”
   （:308-309）。
3. 按编号原文精确匹配取主行：WHERE number = ?（quote.py:288-291 或旧库分支
   :292-296）。SQLite TEXT 主键默认 BINARY 比较，大小写、首尾空格、换行都参与
   匹配，不做归一化或子串搜索；--number 不做格式校验，原样传入
   （quote.py:471）。查不到 -> “错误: 报价编号不存在: <编号>”，退出码 1、
   stdout 为空、不产生输出文件（:297-300）。
   [测试] tests/test_preview_flow.py:226-301；精确匹配在导出侧另有
   tests/test_export_flow.py:320-331（大小写差异、首尾空格差异均不命中）。
   [本次] 未保存编号 Q-NOPE 实测退出码 1、无 other.html 生成（附录 E）。
4. 取明细：SELECT description, quantity, unit_price, line_amount FROM items
   WHERE quote_number = ? ORDER BY position（quote.py:302-306），严格按保存时
   的 position 升序，即输入顺序。
5. 渲染后以 os.open(..., O_WRONLY|O_CREAT|O_EXCL) 独占新建输出文件
   （quote.py:315）：O_EXCL 是并发兜底，目标存在绝不覆盖；os.path.exists 与
   O_EXCL 两道检查之间也不存在覆盖窗口。随后循环 os.write 直到整份 UTF-8
   文档写尽；写 0 字节、写入或关闭抛 OSError 均以退出码 1 结束
   （quote.py:319-340，目标中可能保留此前已写出的部分内容）。输出目录需预先
   存在，否则 O_EXCL 打开即失败（:316-317）。
   [测试] tests/test_write_flow.py:178-300（部分写、0 进度、写失败、关闭失败）。
6. 成功后 print(args.output)：标准输出为 --output 给定的路径原文加换行
   （相对路径就原样输出相对路径），退出码 0（quote.py:342）。

数据来源：客户、合计、note 取自 quotes 行；说明、数量、单价、行金额全部取自
items 行（quote.py:289-306）。预览只反映此前已保存的数据，保存与预览之间没有
内存态共享；预览不重新计算金额（line_amount、total 直接读落库整数）。页面中的
“编号”是命令行传入的 args.number（传入 render_html，quote.py:311），不是库内
回读值；由于查询本身按该值精确匹配，二者正常情况下必然相同。


六、preview（二）：HTML 渲染——note 区域、转义与金额换算
--------------------------------------------------------
[源码] render_html（quote.py:216-272）：

6.1 note 区域的位置与有无
- note 为真值（非 NULL、非空字符串；纯空白字符串也是真值）时，输出一个说明
  区域（quote.py:232-239）：
    <section class="note">
      <h2>客户说明</h2>
      <p class="note-text">{转义后的说明原文}</p>
    </section>
  同时向 <style> 追加一行 “.note-text { white-space: pre-wrap; }”（:233），
  由 pre-wrap 保留空格与换行。
- 该区域插在客户信息定义列表 </dl> 之后、明细 <table> 之前：模板中
  “{note_section}<table>”位于 quote.py:259，</dl> 位于 :258。
- note 为 NULL（省略或空字符串保存的结果）时，note_section 与 note_style 均为
  空串（quote.py:230-231、232），页面不出现说明区域与对应样式。
- note 不参与金额计算，也不影响明细表与总计的任何数值（:216-272 中 note 只
  出现在该区域）。
  [测试] tests/test_note_flow.py:188-217（区域位于 </dl> 与 <table> 之间、
  恰好出现一次、解析文本逐字符等于输入）、:211-217（无说明时无区域）。

6.2 文本转义
  render_html 内 e = html.escape（quote.py:217），默认 quote=True，转义
  & < > " ' 五个字符（&amp; &lt; &gt; &quot; &#x27;）。作用于全部用户文本：
  标题中的编号（:244）、正文编号（:256）、客户（:257）、每条明细说明（:221）、
  note 正文（:237）。数量与金额由整数经 format_yuan 生成，不经转义。
  [测试] tests/test_preview_flow.py:128-224、tests/test_note_flow.py:221-261
  （含既有实体 &lt;原文&gt; 会被再转义一层为 &amp;lt;原文&amp;gt;，且不产生
  script 元素）。

6.3 金额换算（分 -> 元，两位小数）
  format_yuan(cents) = f"{cents // 100}.{cents % 100:02d}"（quote.py:211-213），
  纯整数除法与取模，无浮点。单价、行金额（:223-224）与总计（:267）三处都经此
  函数；数量直接显示整数（:222）；行号列为 position+1（:220）。
  [测试] tests/test_amount_flow.py:115-163 断言 12.50/25.00/3.00/28.00 等显示；
  :165-185 断言 INT64_MAX 分显示 92233720368547758.07。


七、旧库（quotes 缺少 note 列）的兼容边界
-----------------------------------------
[源码] “旧库”指由早期版本创建、quotes 表只有 number/customer/total 三列的
SQLite 文件。

- 直接预览：cmd_preview 先以 PRAGMA table_info 检查列集合（quote.py:286-287），
  缺少 note 列时改查 “SELECT customer, total, NULL ...”（:292-296），一律按
  无说明渲染。只读 URI 打开（:281-283）决定了预览绝不补列、不改任何行。
